# ADR: Staging-first deployment roadmap (four phases, production deferred)

Date: `2026-09-10`

## Summary

**Problem:** The three-phase deployment roadmap (`tmp/implementation-proposal.md`, section 1.1) bundled environment provisioning, application deployment automation, and production deployment tightly together: Phase 2 was "holodeck mirrors the cheapest Linode instance", and Phase 3 deployed staging and production side by side on one paid Linode with automated deploys. That plan assumed an early production deployment the Captain is not ready to fund, and mixed two different concerns (provisioning an environment vs automating deployments into it).

**Decision:** Reorder the roadmap around a long-lived staging environment, with production deferred:

- Phase 2 (leanspec 009) provisions the questr KVM VM (`deploy/kvm-host` IaC: OpenTofu + Ansible) as the **staging** environment: Docker Engine, unattended security updates, Tailscale reachability. No application deployment in this phase.
- Phase 3 (leanspec 010) automates the application installation on staging: Ansible-driven Compose deploys with health-checked rollback, systemd timer-based backup/restore scheduling of the deployed stack (moved from 009 on 2026-09-10; timers over cron per the 009 D5 decision), Caddy TLS via internal CA, Locust limits discovery retuning the Phase 1 memory placeholders (`WEB_CONCURRENCY`, `mem_limit`, `maxmemory`), Bandit static-analysis audit of the codebase (moved from 009 on 2026-09-10, scope purity; triaged before the OWASP review), OWASP deployment review.
- Deploys run on staging for quite some time.
- **Phase 4 (future, no artifacts yet):** production on a cloud service that provides VMs and is supported by OpenTofu (for example Linode), with a configuration similar to the staging VM. No change folder or plan is created now because many feature waves will land before production.

## Context

Money constraint: the Captain does not want to pay for a hosted service yet, so staging runs as a free KVM guest on the EndeavourOS host `enterprise-d`, provisioned from the working base bootstrapped in commit `96dc293f`. The split also fixes a structural risk of the old plan: deploy/rollback automation would have been first exercised on production; now it is exercised on staging where mistakes are free. The "one machine, two environments" concept (staging + prod as isolated Compose projects on one Linode) is abandoned: staging and production are separate machines.

Locust moves from Phase 2 to Phase 3 so limits discovery targets a deployed, self-updating application; the memory retune therefore closes proposal open parameters 1, 2, 8 during Phase 3, before any production-shaped reuse of the numbers.

## Options Considered

### Option A: staging-first, four phases (chosen)

- Matches the budget reality; staging is free and long-lived.
- Deploy automation is proven on staging before it ever touches production.
- Phase boundaries separate provisioning (009) from deployment automation (010).

### Option B: original three-phase plan (rejected)

- Phase 2 validation and Phase 3 deployment both gated on the paid Linode existing; deploy/rollback automation first exercised alongside production; retune and audit squeezed into the same phase as first production deploys.

### Option C: deploy to production now and iterate (rejected)

- Violates the proposal's own safety rule that production must not run on unvalidated numbers, and contradicts the staging-first intent.

## Decision

Adopt the four-phase staging-first roadmap above. Phase 2's earlier "holodeck mirrors the cheapest Linode" framing is dead: validation happens on the questr VM whose shape we control (2 GiB / 2 vCPU, network `vmnet` as the standard). Production intent is recorded here only; no Phase 4 artifacts are created until the Captain is ready.

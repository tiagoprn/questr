# ADR: Redis 7.4.11 license acceptance and noeviction policy

Date: `2026-09-09`

## Summary

**Problem:** Redis must be pinned for the production stack, and its license (RSALv2/SSPLv1 since 7.4) plus its eviction policy needed an explicit decision because Redis holds questr's rate-limit state.

**Decision:** D1: `redis:7.4.11`, exact minor pin; the RSALv2/SSPLv1 license is accepted (Valkey 8 is the documented drop-in alternative if that ever changes). D2: `maxmemory-policy noeviction`: Redis holds rate-limit state (`rate_limiter.py`, `login_rate_limiter.py`, `dual_rate_limiter.py`), which must not silently vanish; with `noeviction`, writes past `maxmemory` fail loudly instead of evicting live state.

## Context

`maxmemory 400mb` sits below the container `mem_limit: 512m` so Redis errors or blocks before the kernel OOM killer acts on the container. Persistence: AOF (`appendfsync everysec`) plus RDB save points, data dir on the `redisdata` volume so state survives container recreation. Config lives in `deploy/redis/redis.conf`, mounted read-only; `requirepass` comes from a Compose secret via the service command.

## Options Considered

### Eviction: `noeviction` (chosen) vs `allkeys-lru`

- `allkeys-lru` fits pure caches; questr's Redis is state (rate limiters), so eviction would silently lift rate limits under memory pressure, exactly when protection matters most.

### License: accept RSALv2/SSPLv1 (chosen) vs Valkey 8

- Accepting avoids a migration; Valkey 8 stays documented as the escape hatch.

## Consequences

- Under `maxmemory` pressure, new writes fail: the app must tolerate failed Redis writes (rate limiting degrades to allowing or erroring, never to silent state loss).
- The pinned tag and the eviction rationale are documented in `deploy/redis/redis.conf` and the first-deployment runbook.

# ADR: Forgejo as the container registry

Date: `2026-09-09`

## Summary

**Problem:** The production Compose stack must pull the app image rather than build on the VM; a registry was needed.

**Decision:** The Forgejo instance at `oa.saga-torino.ts.net:3000` (Tailscale-internal, HTTP, configured as an `insecure-registries` entry) hosts the app image as `oa.saga-torino.ts.net:3000/tiago/questr:<version>`. Images are built on the dev machine by `scripts/deploy/build-and-push.sh` and pushed twice: the pinned semver tag (from `pyproject.toml`, e.g. `0.1.0`) plus `:latest`. Production Compose pulls the pinned version tag; rollback targets the previous semver tag. Reference procedure: `tmp/container-registry.md` (B1/B2 login, C round trip).

## Context

D4 resolved the tag scheme: semver from `pyproject.toml` plus `:latest`; runbooks pin the version tag and never rely on `:latest` for deploys. The registry is reachable only over Tailscale, which is acceptable because deploys run from the dev/ops machine.

## Options Considered

### Option A: Forgejo registry (chosen)

- Already running; zero new infrastructure; auth via existing `pass` token.

### Option B: hosted registry (Docker Hub / GHCR)

- Public exposure or extra credentials for no gain at this scale.

## Consequences

- `deploy/compose.yaml` pins `image: oa.saga-torino.ts.net:3000/tiago/questr:${QUESTR_VERSION:-0.2.0}`.
- VMs need the `insecure-registries` daemon entry (documented in the first-deployment runbook).
- Every pushed semver tag is retained forever: that is what makes rollback possible.

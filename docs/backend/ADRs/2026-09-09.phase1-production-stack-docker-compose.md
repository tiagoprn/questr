# ADR: Phase 1 production stack: Docker Compose, uv image, Caddy edge

Date: `2026-09-09`

## Summary

**Problem:** The repository had only a development Compose file (`docker-compose.yml` with mailpit, published 5432/6379, no app image). There was no production deployment path.

**Decision:** A manually deployable production stack under `deploy/`: multi-stage uv-built image on `python:3.14-slim-trixie` (non-root `app` user), pinned `postgres:18.6` and `redis:7.4.11` with file-backed secrets and memory caps, health-gated Compose wiring with an `internal: true` backend network, and Caddy as the TLS edge (automatic Let's Encrypt on the public machine). The runtime target is docker-compose, not k3s; this supersedes the k3s production target referenced in earlier ADRs (Captain decision, 2026-09-09, `tmp/implementation-proposal.md`).

**Scope note:** Phase 1 delivers artifacts, runbooks, and local validation only. Production deployment happens after Phase 3 (dual-environment automated deploys).

## Context

`tmp/implementation-proposal.md` (three-phase roadmap) defines Work Groups 1A-1G. The dev `docker-compose.yml` stays untouched; the production stack is additive. The app image installs the project non-editable (`uv sync --locked --no-editable`) so `importlib.metadata.version('questr')` resolves.

## Options Considered

### Option A: docker-compose stack (chosen)

- Simplest mechanism that satisfies the roadmap; no cluster operational cost.
- Health-gated `depends_on` orders startup; restart policies cover recovery and boot persistence.

### Option B: k3s (rejected for Phase 1)

- The earlier k3s target was superseded by the Captain's locked decision. CI/k3s explicitly deferred.

## Consequences

- Only Caddy publishes ports (80/443); db and redis sit on an `internal: true` network.
- Healthcheck targets `/health` (liveness-only), never `/health/ready`, so the restart actor never restart-loops a healthy app over a dependency failure.
- Pinned images trade CVE freshness for reproducibility; backup/restore discipline is load-bearing (`scripts/deploy/runbook-restore-test.md`).
- Per-service json-file log caps (10m x 3) in the Compose file; the same caps go into the VM `daemon.json` baseline.

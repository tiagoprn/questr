# ADR: ASGI server for production: Uvicorn, one process per k3s pod

Date: `2026-09-04`

## Summary

An Architecture Decision Record was created to choose the ASGI server that will run the FastAPI backend in production.

**Problem:** The backend needs an HTTP/ASGI server for its k3s deployment on 2 vCPU / 2GB nodes. Candidates were Uvicorn, Granian, gunicorn+gevent, uWSGI, and Hypercorn.

**Decision:** Uvicorn (`uvicorn[standard]`), one process per k3s pod, scaled via replicas. Granian is the documented runner-up and deliberate upgrade path.

- **Workload fit:** FastAPI JSON and DB reads dominate; Uvicorn matches or beats Granian on these endpoints
- **Bottleneck analysis:** on 2 vCPU / 2GB the ceiling is query efficiency and DB connection pooling, not the HTTP layer
- **Ecosystem:** Uvicorn is the FastAPI default, with the deepest documentation and troubleshooting ecosystem

## Context

The production target is k3s, one container per pod, with TLS/HTTP2/HTTP3 termination at the ingress (Traefik ships with k3s). Node budget is 2 vCPU / 2GB per pod. The endpoint mix that will dominate the workload is FastAPI JSON responses and database reads, so server-level throughput on non-DB endpoints is not the deciding factor. What matters is: default-ecosystem support, in-process overhead, and an honest upgrade path if the workload profile changes.

The development server already targets the app factory: the Makefile runs `uv run uvicorn questr.factory:create_app --reload --host 0.0.0.0 --port 8000`. The production command mirrors this entry point without the reload flag.

## Options Considered

### Option A: Uvicorn (`uvicorn[standard]`) — chosen

- **Pros:**
  - FastAPI default; deepest documentation and troubleshooting ecosystem
  - Matches or beats Granian on the endpoints that dominate the workload (FastAPI JSON, DB reads)
  - On 2 vCPU / 2GB, the bottleneck is query efficiency and DB connection pooling, not the HTTP layer, so a faster HTTP server buys nothing today
- **Cons:**
  - No in-pod HTTP/2 (handled at the Traefik ingress instead)
  - Prometheus metrics need an exporter
  - No built-in static-file offload

### Option B: Granian — runner-up / deliberate upgrade path

- **Pros:**
  - In-pod HTTP/2 (not just at ingress)
  - Prometheus metrics without an exporter
  - Static-file offload
  - Stronger websocket-heavy concurrency
- **Cons:**
  - Extension gaps and first-hand compatibility history; requires staging validation before switching (lifespan, websockets/SSE, graceful shutdown)
  - If workers are ever raised beyond 1, the k3s node kernel must be 5.14 or newer
- **Command shape:** `granian --interface asgi --workers 1 main:app`
- **Switch triggers:** any of the Option B pros becomes a real requirement

### Option C: gunicorn + gevent — rejected

- **Cons:** poor results on DB-bound workloads with FastAPI

### Option D: uWSGI — rejected

- **Cons:** legacy

### Option E: Hypercorn — rejected, conditional

- Only if trio or server-side HTTP/3 becomes a requirement; its performance is far behind both Uvicorn and Granian

## Decision

Chosen option: **Option A** — Uvicorn (`uvicorn[standard]`), one process per k3s pod, scale via replicas.

Concretely:

- Dependency: `uvicorn[standard]` is already declared in `pyproject.toml` (`"uvicorn[standard]>=0.32.0"`); no new dependency is needed
- Container CMD: `uvicorn questr.factory:create_app --host 0.0.0.0 --port 8000 --no-access-log` (or `fastapi run` with its built-in production server)
- No `--workers`: k3s replicates pods instead of in-pod worker processes
- k3s resources: memory request 256Mi, limit 512Mi, as a starting point
- TLS/HTTP2/HTTP3 terminated at the ingress (Traefik)

**Special-purpose additions:** read-heavy scaling is a database problem before it is a server problem. Use async SQLAlchemy/asyncpg with an explicit pool sized to the database's max connections, add cache headers/ETags, and consider pgBouncer before adding a second replica.

## Verification

Pending until the deployment work lands. Validation plan:

- Staging run of Uvicorn under k3s: lifespan events, graceful shutdown
- Load check on the JSON/DB-read endpoints to confirm the HTTP layer is not the bottleneck
- If Granian is ever evaluated: staging validation of lifespan, websockets/SSE, graceful shutdown, and k3s node kernel check (5.14+) before raising workers beyond 1
